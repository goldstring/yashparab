Why your feature store is the contract no one signed

Sara Mitchell September 12, 2026 9 min read

Every postmortem I've run on a model that quietly got worse in production ends up in the same place. Not the architecture, not the hyperparameters, not even the data — the culprit is almost always a feature that means two slightly different things depending on who computed it last.

We spent two weeks on exactly this bug during the fraud-detection rebuild I've written about before, and it's worth explaining properly, because the fix wasn't a smarter model. It was treating the feature store schema as a contract with its own version history, not an implementation detail that lives inside someone's notebook.

The symptom looks like model decay

The first sign we saw was a slow, steady drop in precision that didn't correlate with anything obvious — no data volume spike, no upstream outage, no schema migration announced in any channel we were watching. Retraining on fresh data helped for about a week, then the same decay crept back in.

That pattern is the tell. A genuinely stale model degrades and stays degraded until you retrain. A model quietly fighting a definitional mismatch between training and serving degrades, gets patched by a retrain that happens to average over the mismatch, and then drifts again as the two code paths diverge further.

Two teams, one feature name, two definitions

Our training pipeline computed txn_velocity_24h as a rolling count in Spark, windowed on event time with a two-minute allowed-lateness buffer for events that arrived out of order. The serving pipeline computed the same-named feature in a Flink job windowed on processing time, with no lateness handling at all, because nobody had ported that detail over when the streaming version was built six months later by a different team.

Both were reasonable engineering decisions in isolation. Neither team was wrong about their own system. The bug lived entirely in the gap between two definitions that shared a name and nothing else.

The schema is the interface. If two systems can write to a feature under the same name with different semantics, you don't have a feature store — you have two feature stores wearing a trench coat.

What actually caught it

We didn't catch this from a metrics dashboard. We caught it by writing a nightly job that replays a sample of production events through both the batch and streaming feature paths and diffs the output row by row. Anything outside a tight tolerance gets flagged before it ever reaches a training run.

  • Sample 2,000 events per day across peak and off-peak windows.
  • Recompute every shared feature through both pipelines.
  • Fail the build if more than 0.5% of sampled rows disagree beyond tolerance.

The check itself is a plain diff job — the value is in running it on every merge, not in anything clever about the code:

feature_skew_check.py 
import pandas as pd

def check_feature_skew(batch_df: pd.DataFrame,
                        stream_df: pd.DataFrame,
                        feature_cols: list[str],
                        tolerance: float = 1e-3) -> pd.DataFrame:
    """Diff shared features computed by two pipelines on the same events."""
    merged = batch_df.merge(
        stream_df, on="event_id", suffixes=("_batch", "_stream")
    )

    report_rows = []
    for col in feature_cols:
        diff = (merged[f"{col}_batch"] - merged[f"{col}_stream"]).abs()
        mismatched = merged[diff > tolerance]
        report_rows.append({
            "feature": col,
            "sampled": len(merged),
            "mismatched": len(mismatched),
            "mismatch_rate": len(mismatched) / max(len(merged), 1),
        })

    return pd.DataFrame(report_rows)


if __name__ == "__main__":
    report = check_feature_skew(load_batch_sample(), load_stream_sample(),
                                 feature_cols=["txn_velocity_24h", "device_reputation"])
    failing = report[report["mismatch_rate"] > 0.005]
    if not failing.empty:
        raise SystemExit(f"Feature skew detected:\n{failing.to_string(index=False)}")

Treating the schema like an API contract

The long-term fix had three parts, and none of them involved touching the model:

  1. Version every feature definition. txn_velocity_24h_v2 exists specifically because its windowing semantics changed — the old name is retired, not silently redefined.
  2. One computation path, two execution engines. We moved the windowing logic into a shared spec that both Spark and Flink jobs compile against, instead of two teams hand-writing the same logic twice.
  3. Make skew a release blocker. The replay-and-diff job above now runs in CI for any change touching feature logic, not just nightly in production.

What changed

Precision stopped its slow bleed within the first release cycle after the shared spec went in, and — more usefully — we caught two more would-be skew bugs in CI before they ever reached production, in features that had nothing to do with the original incident.

The takeaway

If your training and serving features are computed by different code, in different languages, owned by different teams, assume they will drift — not because anyone is careless, but because that's what happens to any contract nobody is enforcing. Put a test on the boundary before you put more capacity into the model.
